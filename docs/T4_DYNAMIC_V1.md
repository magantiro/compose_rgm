# Dynamic COMPOSE v1 development contract

## Identity

- **Scientific problem:** recover useful coordinated T4 transformations without
  initializing search from stored complete winner routes.
- **Primary output:** executor-verified dynamic programs and complete
  score-versus-call curves on three declared delta-0.4 development cells.
- **Claim under test:** three generic capabilities diagnosed from Dynamic-v0
  failures improve effective route support without storing or retrieving the
  inspected Full-146 solutions.
- **Validation setting:** 5HT1B seed 0, BRAF seed 1 and JAK2 seed 1, replicate 0,
  under the frozen T4 endpoint gates and docking protocol.
- **Primary baselines:** existing Full-146 and Dynamic-v0 outcomes, both reused
  read-only. No comparator is redocked.
- **Declared support:** exact 48-slot molecular graphs with 1 to 40 active heavy
  atoms; the production atom, charge, bond and executor support; complete
  programs of at most 32 primitives and eight blocks. Stereochemical and
  formal-charge editing remain outside proposal support.

This is winner-informed development. Full-146 routes may be inspected only as
answer-known diagnostic teachers. They may not be copied into the Dynamic-v1
runtime grammar, sampler, initial archive or target-specific configuration.

## Frozen inputs and separation

The following scientific objects remain immutable:

- the Full-146 controller, library and outcomes;
- `src/compose_v4/control/dynamic_program_synthesis.py` and all Dynamic-v0
  artifacts;
- the live Dynamic-v0 5HT1B invocation and its query ledger;
- the original T4 seeds, endpoint gates, docking oracle and call accounting.

Dynamic-v1 must use a new implementation module, schema, configuration and
artifact namespace. One shared v1 law is used for all three cells. Target names,
known endpoint strings, known scores and stored route payloads are forbidden in
the deployed v1 proposer.

## Zero-oracle reachability gate

Before a scored run, compile the inspected Full-146 transformations through the
generic Dynamic-v1 interfaces with module parameters supplied by the diagnostic.
This is teacher-forced support analysis, not autonomous recovery. For each cell,
record:

- the input route/program identity and immutable source artifact hash;
- whether Dynamic-v0 already represents the transformation;
- whether Dynamic-v1 represents it;
- the minimum number of generic modules required, or an explicit abstention;
- exact primitive and block counts;
- exact endpoint and full-state replay agreement;
- compiler failures and excluded route portions;
- coverage and execution precision separately.

The reachability tool must accept route data as a versioned input. No inspected
route parameters may appear as constants in production Dynamic-v1 code.

## Authorized Dynamic-v1 capabilities

Only these additions are in scope.

1. **Protected ring-path remodeling.** A parameterized module may remove or
   replace a bounded cyclic path between retained boundary atoms and reconnect
   those boundaries when the exact executor admits the complete sequence.
2. **Joint substituted-ring construction.** One parameterized protected module
   jointly chooses ring anchors, size, C/N/O pattern, cycle bond pattern and a
   bounded set of substituent branches, then executes the complete construction
   before endpoint eligibility is evaluated.
3. **Bounded context-conditioned binding enumeration.** For a chosen module or
   short composition, enumerate a capped deterministic set of compatible
   sites/parameters and rank them only by declared non-oracle structural
   quantities and within-run charged history. Missing task scores are never
   invented.

Every primitive remains exact-executor validated. Structural validity holds at
each committed state, while QED, synthetic accessibility, similarity and
docking are endpoint properties of the protected complete proposal.

## Scored comparison

Launch only after the live Dynamic-v0 5HT1B unit becomes durable and the
zero-oracle gate, focused tests and remote preflight pass.

| Setting | Value |
| --- | --- |
| Cells | `5ht1b_0`, `braf_1`, `jak2_1` |
| Controller/docking seeds | identical to replicate 0 of the current diagnostic |
| Similarity threshold | strict `> 0.4` |
| Other endpoint gates | QED `> 0.6`, SA `< 4.0` |
| Molecular support | at most 40 active heavy atoms |
| Program work | at most 32 primitives and eight blocks |
| Oracle ceiling | 1,000 distinct candidate dockings per cell; 3,000 total |
| Concurrency | at most three one-CPU workers; no GPU |
| Retry/confirmation | none |
| Early stop | existing frozen competitive-plateau rule |

Preserve every attempted proposal and reason code. Report best score versus
actual charged calls, candidate yield, duplication, execution/eligibility
funnels and proposal time. Compare BRAF retention, JAK2 gap closure and 5HT1B
binding improvement descriptively. Docking stochasticity and the single
development replicate limit causal or general performance claims.

## Acceptance

1. Dynamic-v0 source and live artifacts are unchanged.
2. V1 contains exactly the three authorized generic capabilities and no
   target-specific payload.
3. Teacher-forced artifacts are deterministic, hash-bound and use zero task
   oracle calls.
4. Every admitted forced program exact-replays to its declared endpoint; report
   coverage and precision, including failures and abstentions.
5. Focused happy-path, boundary, malformed-input, determinism, provenance and
   executor-replay tests pass; formatting, lint and repository verification run
   at the launch boundary.
6. The worktree and generated launch artifacts are inspected, committed and
   pushed before a remote scored launch.
7. No remaining-cell evaluation or further controller change follows
   automatically.
