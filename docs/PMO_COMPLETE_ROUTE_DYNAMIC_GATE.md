# PMO complete-route Dynamic gate

This is the zero-oracle integration gate authorized after the static 384-call PMO
factorial returned `NO_PROMOTION`. The earlier experiment remains immutable. It used
at most eight route primitives, restarted every round from the same initialization
parents, and did not permit scored children to become later parents. It therefore did
not test the intended recursive route-distilled Dynamic controller.

## Scientific question

Can a clean, task-family-held-out proposal law place complete dependency-aware PMO
programs inside the actual 32-primitive runtime, while the unchanged Dynamic-v0 lane
preserves exploration and FiberControl can exploit already observed reward along a
recursive archive?

The generated object is a complete legal COMPOSE program with at most 32 primitives
and eight dependency regions. The clean proposal checkpoint contains only generic
program length and position-conditioned executor-rule probabilities. WHERE/HOW is
bound at runtime by the previously frozen graph-conditioned legal-successor policy.
It contains no task, lineage, molecule, endpoint, absolute address, action, or route.

## Frozen development tasks and the important abstention

The tasks were declared before this gate:

| task | held fold | exact route lengths | complete runtime witnesses |
| --- | ---: | --- | ---: |
| Celecoxib rediscovery | 1 | 29–31 | 15/15 |
| GSK3B | 0 | 27–33 | 23/24 |
| Perindopril MPO | 2 | 38–67 | 0/16 |

Perindopril therefore provides local-decision supervision and historical recursive
replay evidence only. The gate must not truncate those routes and describe them as
complete-route support.

## Gate

At every distinct state in the selected frozen routes, the audit draws one candidate
from each of three actual proposal mechanisms under a matched budget:

1. the old eight-primitive transition prior;
2. unchanged Dynamic-v0;
3. the new complete-route proposal law.

After candidate generation is locked, answer-known routes measure exact endpoint and
transformation-equivalent support. Productive continuation rank is reported as the
two factors the runtime actually uses: generic executor-rule rank and graph-conditioned
WHERE/HOW rank within that rule. Teacher actions are never inserted into a candidate
fiber.

Separately, existing scored PMO outcomes are replayed through a shared recursive
archive. Children become eligible parents in later rounds. FiberControl and a
reward-blind comparator receive the same historical candidate graph, call budget, and
seed. Candidate scores remain hidden until selection. This is retrospective replay,
not prospective evidence.

Promotion requires both:

- support for a known productive complete program, not component recall alone;
- historical reward enrichment by FiberControl over the matched blind replay, with an
  improving multi-generation lineage.

Failure is preserved as `NO_PROMOTION`; the rule is not relaxed.

## Final result

The engineering gate passed exact runtime replay and historical recursive-control
checks. Its `PROMOTE_TO_SCORED_CONTRACT` label means only that the evidence was complete
enough to run the stricter gap analysis. It is **not** scored-launch authorization.

The authoritative scientific decision is
`gap_analysis.json: NO_SCORED_LAUNCH_PRODUCTION_SUPPORT_INSUFFICIENT`:

- Celecoxib produced 7/34 teacher-scale programs; GSK3B produced 21/44. Every
  generated complete program exact-executed.
- Neither task produced one exact or transformation-equivalent teacher endpoint.
- Every complete known Celecoxib/GSK3B trace has zero probability under the current
  autonomous production factorization because at least one productive continuation is
  absent from its legal proposal fiber.
- Perindopril has no complete witness within 32 primitives, so success requires a
  route-scale jump followed by recursive continuation.
- The existing historical FiberControl ledger is recursive but contains no program
  longer than seven primitives. It therefore does not validate the intended
  jump-plus-refinement mechanism.

The next controller should jointly model a dependency-region program latent rather
than draw primitive rules and WHERE/HOW choices independently. No scored PMO run should
launch until the zero-oracle requirements in `gap_analysis.json` pass.
