# T4 FiberControl route-recognition diagnostic

## Identity and scope

The scientific question is whether the existing FiberControl value model can recognize a
known high-value complete protected COMPOSE program when that program is present in a
same-source candidate menu. The generated object under evaluation is one complete
executable program from an exact source state to a queryable endpoint. The primary output
is the program's rank under the unchanged `ProgramValue` law after chronological historical
outcomes from that cell.

The central diagnostic claim is deliberately narrow: if a strong program ranks well, the
historical evidence is consistent with proposal support being the dominant missing piece.
If it ranks poorly, proposal repair alone is insufficient evidence that FiberControl will
select it. This is retrospective recognition, not autonomous route generation, causal
evidence, prospective docking, or a T4 performance estimate.

Three cells are used because their immutable program-curriculum archives contain exact
source, program, trace, endpoint, call index, and docking-score provenance. The probe is
selected by one fixed rule: the lowest historical score among candidates observed after at
least four earlier same-cell candidate outcomes. Four observations are required because the
production `ProgramValue` abstains below that count.

## Leakage and temporal contract

At each chronological prefix, the model is fitted only on outcomes with smaller historical
query indices. The probe score and every later score remain hidden. The candidate menu
contains the unobserved exact same-source route siblings plus deterministic ordinary shallow
COMPOSE proposals generated without oracle calls. The probe is injected only because this
is a known-answer recognition test. Its measured score is reported after ranking and never
enters a feature, fit, or selection decision.

The curriculum routes are complete protected programs with one queryable endpoint. Their
primitive interior is not treated as a sequence of FiberControl decisions because protected
intermediates need not satisfy the endpoint contract. Consequently, this diagnostic tests
three complete-program decisions across targets, not a fabricated multi-boundary trajectory.

The complete frozen recipe is
[`configs/t4_fiber_route_recognition_v1.json`](../configs/t4_fiber_route_recognition_v1.json).
It authorizes no docking, oracle, Modal, compiler, or integrated-controller change.

## Interpretation gates

- `rank <= 5` on at least two of three probes supports proceeding with the proposal-mixture
  hypothesis while retaining the existing value model.
- Poor rank on two or more probes is a direct warning that the current feature/value law
  will not reliably exploit route proposals even when they are exposed.
- A rank result cannot establish autonomous support, because the known program is injected.
- Family indicator fields unavailable for the older complete-route records are set to zero,
  never inferred from endpoint identity. This is an applicability limitation of the current
  FiberControl representation and is reported explicitly.
