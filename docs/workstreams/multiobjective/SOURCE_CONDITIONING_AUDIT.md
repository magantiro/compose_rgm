# Source-conditioned versus global Pareto — the fairness audit

**Artifact status: `DESIGN_ONLY`.** No baseline has been installed, no baseline
has been run, no compute has been spent. Every cell below resolves to a file and
line in an official repository, a paper section, or a committed artifact in this
repo. Cells that do not so resolve are marked `UNVERIFIED` and stay out of the
main table.

---

## Why this audit exists

The COMPOSE Pareto task is **source-conditioned**. Each source molecule has its
own reachable region: the endpoints attainable in `BUDGET = 6` edits from that
exact molecule under the frozen process
(`modal_apps/pareto_control_app.py:102-103`, branch `codex/compose-pareto-control`;
`BUDGET` is annotated `#: Frozen by PROTOCOL.md section 7.1. Not tunable here.`).

A de novo generator has the whole of chemical space. Placing its pooled global
front beside COMPOSE's per-source fronts would grant it a strictly larger
reachable set while the table caption said "same task". That is the single most
damaging error available in this block, and it is silent — the numbers look
comparable.

So there are two panels, and nothing crosses between them.

| | Panel A | Panel B |
|---|---|---|
| name | COMPOSE-native source-conditioned control | ordinary global multiobjective competence |
| task | start from a supplied molecule, fixed edit budget, preference-conditioned output | shared global task freedom, shared objective budget |
| members | COMPOSE fixed-preference control; generate-and-rank P3/P4; empirical-family reference ablation; any published method natively supporting supplied-source semantics | HN-GFN, InversionGNN, COMPOSE, under a separately frozen common benchmark |
| aggregation | per-source fronts, then source-level paired bootstrap | one front per method on the common task |
| caption must say | same-state capability experiment | conventional Pareto-competence comparison |

The rule is enforced in code, not only in prose:
`src/compose_v4/experiments/multiobjective_qualification.py::assert_not_cross_panel`
raises on a Panel A versus Panel B comparison, and
`tests/test_multiobjective_qualification.py::test_cross_panel_comparison_raises`
holds it.

---

## The three questions each method must answer

A method enters **Panel A** only if all three are natively `YES`:

- **(a) supplied source** — can it begin from an exact molecule we hand it?
- **(b) edit budget** — can it be held to a fixed edit / trust-region budget
  measured from that molecule?
- **(c) preference-conditioned output** — can it produce output conditioned on a
  requested preference vector, from that source?

`UNVERIFIED` on any axis keeps a method out of Panel A **and** out of the main
table until the cell is settled from a primary source.

## HN-GFN — Panel B only

Official code `https://github.com/violet-sto/HN-GFN`, commit
`90078b8ceeee3e907deeced9b096a6e395b71177` (2023-12-25), MIT
(`LICENSE`). Paper: Zhu, Wu, Hu, Yan, Hsieh, Hou, Wu, *Sample-efficient
Multi-objective Molecular Optimization with GFlowNets*, NeurIPS 2023,
arXiv:2302.04040.

| axis | verdict | evidence |
|---|---|---|
| (a) supplied source | **NO** | `main.py:145` — the rollout body opens `m = BlockMoleculeDataExtended()`, an **empty** block molecule, on every trajectory. `mol_mdp_ext.py:193-194` — `def reset(self): self.molecule = BlockMoleculeDataExtended()`. There is no code path that seeds a trajectory from a supplied SMILES. |
| (b) edit budget | **NO** | the only trajectory action is fragment append: `main.py:176` `m = self.mdp.add_block_to(m, *action)`, with `mol_mdp_ext.py:169 add_block_to`. `remove_jbond_from` exists on the MDP but is never called in a rollout. With no source there is no trust region to define. Paper §4: "the molecular graphs are generated by sequentially attaching a fragment, which is chosen from a predefined vocabulary of building blocks, to an atom of the partially constructed molecules. The maximum trajectory length is 8". |
| (c) preference-conditioned | **YES** | `main.py:226-227` `if self.args.scalar == 'WeightedSum': raw_reward = (weights*score).sum()`; the hypernetwork conditions the output heads on the weight vector (`model_pred_hyper.py`). Weights are drawn per batch from a Dirichlet (`main.py:239`). |

**Panel: B.** HN-GFN is a genuinely preference-conditioned multiobjective
molecular Pareto generator — which is precisely why it must be in the paper, and
precisely why it cannot be in Panel A. It answers the reviewer question *"why not
use a purpose-built preference-conditioned sample-efficient molecular Pareto
generator?"* on the global task, and it cannot answer the same-state question at
all, because it has no notion of a state we supply.

### Its scalarization is linear, and stays linear

`--scalar` defaults to `WeightedSum` (`main.py:54`, `main_mobo.py:62`). COMPOSE
uses an augmented Chebyshev (`pareto_control.py`, `CHEBYSHEV_RHO = 1e-3`).

**We do not supply HN-GFN a Chebyshev to match ours.** That is the standing
main-lane decision, and it is right: changing a competitor's internal
formulation is changing the competitor. Its opt-in `Tchebycheff` branch
(`main.py:229-230`, `raw_reward = (weights*score).min() + 0.1 * (weights*score).sum()`)
is an augmented max-min with no ideal point and a hardcoded 0.1 — it is not
classical Chebyshev either, so selecting it would not even achieve the symmetry
it appears to offer. It may appear only as a clearly labelled secondary.

Consequence to state in the caption, not to correct for: a weighted sum can only
select points on the convex hull of a front, so HN-GFN is structurally unable to
report nonconvex front regions that a Chebyshev scalarization can reach. That is
**a property of the method**, and it is never to be reported as a COMPOSE win.

### Two verified facts that make Panel B fairer than expected

1. **The DRD2 oracle is the same model file.** HN-GFN ships
   `oracle/scorer/drd2/clf_py36.pkl`, sha256
   `dbc473fca922c834dbaee6eaba832caaff26d4f891734078fb1af359a111100f`,
   35,417,609 bytes (measured 2026-08-13). COMPOSE's frozen oracle manifest
   `artifacts/oracles/drd2_svm_v1/drd2_oracle_manifest.json` records
   `pickle_sha256` and `pickle_bytes` with **exactly those values**, and the same
   fingerprint definition — `AllChem.GetMorganFingerprint(mol, 3, useCounts=True,
   useFeatures=True)` folded to 2048 by identifier modulo, int32 counts
   (`drd2_scorer.py::fingerprints_from_mol` versus the manifest's `fingerprint`
   block). Both descend from the Olivecrona/REINVENT DRD2 activity SVM.

   **What this licenses:** the potency objective can be the same object for both
   methods, so a reviewer cannot object that COMPOSE and HN-GFN were scored by
   different DRD2 models.

   **What it does not license:** a claim that the two produce bit-identical
   scores. COMPOSE consumes extracted numpy parameters, HN-GFN calls sklearn
   `predict_proba`. Bit-level parity is `UNVERIFIED` and would need its own
   known-answer test against the manifest's committed `reference_scores`.

   **And the gap is now known to be wider than "different implementations".**
   `docs/ORACLE_BATCH_INVARIANCE_DEFECT.md` records that COMPOSE's *own* DRD2
   oracle is **batch-size dependent**: `drd2_oracle.py:213`
   `kernel @ self.dual_coef + self.intercept` matches across batch shapes on only
   13/512 molecules, max |d| 1.82e-14, because `(1,N) @ (N,)` dispatches to a dot
   product and `(B,N) @ (N,)` to GEMV with a different accumulation order. So the
   same molecule scores differently depending on how many were asked about at
   once — and main-lane Decision 1 responds by **pinning all claim-bearing
   COMPOSE decision code to the legacy `B=1` path**.

   HN-GFN scores in batches (`drd2_scorer.get_scores` takes a list). Any future
   parity test must therefore fix the batch shape before it can mean anything,
   and "same model file" is further from "same scores" than it first appears.
   The magnitude is chemically meaningless and is *exactly* the size that flips
   an `argmax` tie over a ~586-wide fiber, which is why the pinning exists.

2. **Objective availability.** `oracle/scorer/scorer.py:38-52` natively supports
   `qed`, `sa`, `mw`, `logp`, `penalized_logp`, plus `drd2`, `jnk3`, `gsk3b`,
   `seh`. COMPOSE's `D` axis is built from `QED.qed` and `Crippen.MolLogP`
   (`pareto_control_app.py:213-218`), both of which HN-GFN's scorer already
   computes. So Panel B needs an **objective wrapper**, not a new objective.

### The efficiency asymmetry — the largest unresolved fairness risk

HN-GFN's advertised sample efficiency is measured in **true-oracle calls**, and
those are bounded by `num_init_examples=200` plus
`num_outer_loop_iters=8 x num_samples=100` (`main_mobo.py:50-52`) — a **1,000-call
budget**. The true oracle is touched only at
`main_mobo.py:393 scores_dict = oracle.batch_get_scores(picked_mols)`, once per
outer round. The GFlowNet itself trains against a **learned proxy**:
`main_mobo.py:211 raw_reward, score = self.proxy(m, weights)`.

COMPOSE pays the frozen evaluator directly at every decision — the committed
smoke records `verified_pref` at a mean of 269,884 distinct evaluations per
source (`diagnostics/pareto_semantic_oracle_accounting.json`,
`PARETO_ORACLE_REQUEST_AUDIT.md`).

Reported on `unique oracle evaluations` alone, HN-GFN would appear over two
orders of magnitude cheaper, and that number would be measuring **amortization,
not efficiency**. The cost has moved onto an axis the comparison does not show.

The response is not to handicap either method. It is to add the missing axis:
`surrogate_calls` is a first-class resource axis in
`multiobjective_qualification.py`, and `oracle_efficiency_verdict` returns
`INCOMPARABLE_SURROGATE_ASYMMETRY` rather than a number when one method consumes
a learned surrogate and the other does not. Both axes are then reported side by
side, each named.

This restates, from the code, a risk the predecessor lane had already recorded
as an unresolved fairness blocker in
`docs/workstreams/baseline-qualification/DECISION_LOG.md` (branch
`codex/compose-baseline-qualification`).

## InversionGNN — Panel B, and blocked on code defects

Paper: Niu, Gao, Xu, Liu, Bian, Rong, Huang, Li, *InversionGNN: A Dual Path
Network for Multi-Property Molecular Optimization*, ICLR 2025, arXiv:2503.01488.
Official code `https://github.com/ivanniu/InversionGNN`, commit
`cfdf1d9a981ca4ce5dd7293dc38373ddf9377718` (2025-08-29).

| axis | verdict | evidence |
|---|---|---|
| (a) supplied source | **YES, mechanically** | the optimizer iterates from a molecule: `molecular/denovo.py:21 start_smiles_lst = ['C1=CC=CC=C1NC2=NC=CC=N2']`, and the paper's §4.3 formulates each step as `x^{t+1} ∈ P^t ⊆ N(x^t)`. **But** it is a hardcoded list with no CLI argument, and the paper's own benchmark protocol seeds from a trivial fragment and calls the setting de novo design. |
| (b) edit budget | **NO** | there is no similarity constraint and no maximum-edit constraint relative to the source. `similarity()` in `molecular/chemutils.py` feeds the diversity metric only. Termination is by iteration count and oracle budget (`molecular/denovo.py`). |
| (c) preference-conditioned | **YES** | a weight vector is supplied at optimization time and solved by an Exact-Pareto-Optimal linear program (`molecular/epo_lp.py::EPO_LP`), with no retraining per weight. |

**Panel: B.** (b) is `NO`, so Panel A is closed. It is a legitimate Panel B
member and a good one: it is the current ICLR-2025 gradient-based Pareto search
for discrete chemical space, and it targets approximate full-front coverage.

### Blockers, each verified in the checked-out tree

1. **No checkpoint, and the loader is empty.** `molecular/denovo.py:75-76`:
   `model_ckpt = ""` immediately followed by `gnn = torch.load(model_ckpt)`. No
   checkpoint is shipped. The surrogate must be trained from
   `data/zinc_label.txt`, which is also not shipped.
2. **A signature mismatch that must raise.** `molecular/denovo.py:107` calls
   `optimize_single_molecule_one_iterate_epo_v3(smiles, gnn, preference,
   property_num, topk=topk, epsilon=epsilon)`, while
   `molecular/inference_utils.py:153` defines
   `def optimize_single_molecule_one_iterate_epo_v3(smiles, gnn, topk, epsilon)`
   — four parameters. The call passes four positionally and then `topk` again by
   keyword. This is reached once the molecule has grown past the branch
   condition, so it is not an edge case.
3. **No license.** There is no `LICENSE` file anywhere in the tree and the
   GitHub API reports none. Default all-rights-reserved: no redistribution and
   no derivative rights are granted. **Vendoring its code into this repository
   is not permitted**, unlike GB-GA (MIT) which the predecessor lane vendored.
4. **No DRD2.** The paper and repo cover GSK3β, JNK3, QED, SA (and `logp` in
   code). COMPOSE's potency axis is DRD2. Panel B's objective pair therefore has
   to be chosen so that both methods can compute it natively — see PROTOCOL.md.

Defect 2 is on the boundary the baseline policy draws. Repairing a call-site
arity mismatch to make the authors' own function callable is *environment and
compatibility work*, in the same family as the MARS sklearn fix, which
"restores originally intended oracle behaviour rather than changing the
algorithm". Supplying a checkpoint the authors never released, or choosing the
surrogate's training data, is **not** — that is inventing the method's learned
component. The line is drawn in PROTOCOL.md and the fallback is stated there.

**Recommended status: `NUMERIC_BASELINE_IF_QUALIFIED`, conditional on
(i) the arity fix being confirmed as the authors' evident intent, and
(ii) surrogate pretraining being reproducible from the stated ZINC-250K
labels.** If either fails, InversionGNN goes to related work rather than being
reconstructed.

## OP-GFN — do not include

Paper: Chen and Mauch, *Order-Preserving GFlowNets*, ICLR 2024, arXiv:2310.00386.
Official code `https://github.com/yhangchen/OP-GFN`, commit
`369e910891d3c9e20b8272d8291310fb9cc11c4d` (2024-03-11).

| axis | verdict | evidence |
|---|---|---|
| (a) supplied source | **NO** | de novo fragment assembly from an empty graph: `multi/gflownet/algo/graph_sampling.py:79 graphs = [self.env.new() for i in range(n)]`, with `multi/gflownet/envs/graph_building_env.py:139-140 def new(self): return Graph()`. |
| (b) edit budget | **NO** | no source exists, so no trust region is definable. |
| (c) preference-conditioned | **NO** | `multi/gflownet/tasks/seh_frag_moo.py:388` sets `"do_ordering": True if args.type == 'ordering' else False` while `:398` and `:414` set `"preference_type": "dirichlet" if args.type == 'pref' else None`. In OP-GFN's own mode `preference_type` is `None`. `--type pref` is the preference-conditioned **PC-GFN baseline** it is compared against, not OP-GFN. OP-GFN learns an order-preserving reward that yields the whole front; you cannot ask it for a specific weight vector at inference. |

**Verdict: exclude from the numerical table; cite in related work.** Three
independent reasons, any one sufficient:

- The charter admits it *only if* official runnable code plus a thin adapter
  suffice. They do not: it is not preference-conditioned, which is the property
  the Pareto block is about.
- Its objectives are asserted closed: `seh_frag_moo.py:62`
  `assert set(self.objectives) <= {"seh", "qed", "sa", "mw"}`. Neither DRD2 nor
  a COMPOSE-compatible potency axis is reachable without editing the method.
- **Licensing.** `LICENSE.md:1` is Creative Commons
  **Attribution-NonCommercial-NoDerivatives 4.0**. NoDerivatives means an
  adapted version is outside the licence grant — so the very thin adapter that
  would make it runnable here is the thing the licence does not permit us to
  distribute. This is a hard stop that no amount of engineering resolves.

There is also no per-molecule or oracle-budget mode: one run is a full training
(`num_training_steps: 20000` at `global_batch_size: 64`) with `"device": "cuda"`
in the task config. A twelve-molecule smoke is not expressible.

## What this audit does not resolve

- Whether Panel B's common benchmark should reuse the predecessor lane's frozen
  five-task `CONVENTIONAL_SUITE.md` or needs a separate multiobjective freeze.
  Recorded as an open decision in `DECISION_LOG.md`; it is main's call, and it
  must be frozen **before** any outcome is seen.
- Whether COMPOSE can even *enter* Panel B. COMPOSE's process is defined as
  editing from a supplied source; a global de novo COMPOSE arm is not a thing
  that currently exists, and inventing one to fill a table cell would be
  building a new method. If it cannot, Panel B is a competence comparison
  **among externals** with COMPOSE absent, and the paper says so.
- Bit-level DRD2 parity between HN-GFN's sklearn path and COMPOSE's numpy path.
